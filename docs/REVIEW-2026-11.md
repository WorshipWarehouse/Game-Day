# Independent review — GameDay 1.0.0 (commit `aed5a41`)

Reviewer role: senior Android systems engineer, adversarial. Everything here comes from reading the
source, running the build and tests in a clean environment, and static analysis — not from the
project's own completion report.

Result: **accept with corrections.** Ten defects were found and fixed; the architecture decision
stands, with stronger evidence (see [RESEARCH-PHASE2.md](RESEARCH-PHASE2.md) and
[decisions/0002](decisions/0002-isolation-and-runtime-feasibility.md)).

## 1. Method

1. `git log`, full source inventory (10,317 Java lines across four modules).
2. Read every security- and lifecycle-critical source: runtime backend, package inspection and
   verification, installer session handling, both update managers, settings, diagnostics, provider,
   base activity, startup and home screens.
3. Ran the test suite, the build, and **Android Lint** (which the project did not run before).
4. Re-verified APK signing, permissions, `minSdk`/`targetSdk`, DEX class count and absence of native
   code or third-party runtime dependencies.
5. Audited the trust-on-first-use model and the two update chains for bypasses.
6. Independently re-ran runtime research with new candidates (Phase 2).

## 2. Defects found and fixed

| # | Severity | Defect | Effect on the target device | Fix |
| --- | --- | --- | --- | --- |
| 1 | **Critical** | `PackageInstallerHelper` called `SessionParams.setInstallReason()` unconditionally | API 26 method; on Fire OS 6 (API 25) **every** staged install throws `NoSuchMethodError` — the entire update/install feature was dead on the primary target | Guarded by `SDK_INT >= 26`; Lint now gates this class of bug in `scripts/test.sh` |
| 2 | **High** | `InstallResultReceiver` ignored `STATUS_PENDING_USER_ACTION` and its `EXTRA_INTENT` | On platforms that hand the confirmation back instead of showing it, a committed session would wait forever and the update would never complete | Receiver now forwards the confirmation intent |
| 3 | **High** | `StartupActivity` performed the GameDay release check on the startup path, before routing | Startup blocked on up to several HTTPS requests (15 s timeout each); on a slow link the splash could sit for a minute, defeating the <3 s target | Routing happens first; the check runs on a daemon thread afterwards and its result is persisted |
| 4 | **High** | `SettingsStore.resetToDefaults()` cleared *all* preferences | "Restore default configuration" silently erased the pinned NFL signing certificate, re-opening trust-on-first-use to any package that had replaced the app | Reset now preserves the signer pin, version facts and last-known-working version; the keep-list is exposed for the UI (`preservedAcrossReset`) |
| 5 | Medium | `BaseActivity` set `menuHandled` but never cleared it except in `onBackPressed` | `MENU` opened Settings **once per screen instance**, then stopped working | Flag resets on each MENU key-down |
| 6 | Medium | Long-press `BACK` called `finishAffinity()` from any screen | A held Back button in a sub-screen silently terminated the app, contradicting the documented "only home exits" behaviour | Guarded by `isTaskRoot()`; elsewhere a long press is just Back |
| 7 | Medium | `GameDayUpdateManager.storedManifest()` reconstructed `minSdk` (hard-coded 25) and `publishedAt` (from the local check time) | The cached manifest, shown in the UI and exported in diagnostics, **misreported the published artefact** | Real `minSdk` and `publishedAt` are stored with the manifest and read back |
| 8 | Medium | `NflUpdateManager` could not distinguish an update from a reinstall | A reinstall (sign-in and downloads lost) looked identical to a successful update | Tracks `firstInstallTime`; a changed value is reported as a reinstall with likely data loss |
| 9 | Low | Every release check re-downloaded the full release list | Wasteful on a 1.5 GB device and against GitHub's 60 requests/hour unauthenticated limit | `HttpFetcher` supports `If-None-Match`; a 304 short-circuits the check without parsing releases |
| 10 | Low | `NativeHostRuntime.install()` reported a missing install permission as `VERIFICATION_FAILED` | Misleading diagnostics for the most common user-fixable failure | New `RuntimeError.PERMISSION_REQUIRED` code |

All ten were fixed in this pass, with the version bumped to 1.0.1 (`versionCode` 2) so a corrected
build can install over the reviewed one.

## 4. Security review of trust-on-first-use

The model is sound for this deployment, with limits that are now documented rather than implied:

- The pin is recorded from the **installed** package at first observation and compared on every
  later observation; a mismatch blocks launching and is surfaced in Recovery.
- TOFU trusts whatever is installed the first time. GameDay ships no known-good NFL certificate on
  purpose — hard-coding one would rot and would be unverifiable in this repository. The Appstore is
  the trust anchor.
- Comparison uses the **first** signer digest. APK Signature Scheme v3 rotation and signing lineages
  are not evaluated (they do not exist on API 25), so a legitimate future key rotation would appear
  as a mismatch and require re-trusting. That is the safe failure direction.
- The pin survives configuration reset. It is cleared only by a full GameDay data reset, which the UI
  describes as such.
- Update verification order is correct: package identity → signature → version monotonicity →
  `minSdk`/ABI → device features → storage, and only then `PackageInstaller`. A failure at any step
  deletes the download.

## 5. Assumptions that remain unsupported by evidence

These are now listed as unverified rather than assumed:

1. That the Amazon Appstore deep link `amzn://apps/android?p=…&intent=app_update` behaves as
   documented on Fire OS 6.
2. That Fire OS 6 permits `REQUEST_INSTALL_PACKAGES` grants and shows a usable install confirmation.
3. That the NFL app is reachable through a leanback launch intent on this build (metadata says yes;
   the device has not been asked).
4. That a Fire TV exposes usage access at all (needed only for coarse foreground detection).
5. That the Amazon Appstore is the `installerPackage` for the guest.
6. That protected playback is unaffected — plausible because GameDay never touches the media path,
   but not observed.

`./scripts/qualify.sh` collects evidence for all six in one run.

## 6. Runtime question

Phase 2 added BlackBox/forks, managed profiles, closed-source VM apps, Anbox, Cuttlefish and ARC.
None changes the conclusion: no rootless guest environment on API 25 preserves protected playback,
and no compatibility layer raises the guest's API level without root or a system signature. The one
genuine isolation mechanism — a managed profile — is now **measured** on-device
(`IsolationAssessment`, `isolation` section in diagnostics) instead of being asserted. Decision C, as
recorded in ADR 0002.

## 7. Not covered by this review

- Device behaviour of any kind (no Fire TV attached).
- Full line-by-line review of the six secondary UI screens (they were read for lifecycle and
  navigation correctness, not for visual detail).
- The compatibility test application's media pipeline beyond its structure.
- Long-run stability, thermal behaviour and real FPS.

## 8. Recommendation

Ship the corrected build, then run `./scripts/qualify.sh` on the target device before any claim of
hardware support. Keep describing the product as a host and launcher: it is not an emulator, and the
documentation now says so in every place that matters.
